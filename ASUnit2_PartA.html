Exam focus

What Part A is testing

Section A is about analysis and design. Students usually receive a scenario and must design parts of a system before implementation. The highest-value areas are: identifying data requirements, designing ERDs and data tables, creating or tracing algorithms, preparing class diagrams where required, and justifying the solution clearly using technical terms.

Part A checklist

Step 1

Scenario analysis

Before drawing an ERD or writing pseudocode, break the scenario into a clear list of data, processes and requirements.

Find the data

  • Underline nouns: customer, booking, holiday, staff, payment.
  • These usually become entities, classes, files or records.
  • Look for IDs: CustomerID, BookingID, TransactionID.

Find the processes

  • Circle verbs: store, search, book, calculate, validate, update.
  • These become methods, algorithms or justification points.
  • Keep answers linked to the listed requirements.
Exam routine: identify entities first, then data fields, then relationships, then the algorithm/process required. This prevents your ERD, data table and justification from contradicting each other.
Step 2

Entity Relationship Diagrams (ERDs)

An ERD shows how data is structured and connected. Students should include entities, attributes, primary keys, foreign keys and cardinality.

How to build an ERD
  1. Identify entities from the scenario.
  2. Add attributes for each entity.
  3. Choose a primary key for each entity.
  4. Add relationships and cardinality.
  5. Add foreign keys where records connect.
  6. Resolve many-to-many relationships with a linking entity.
What the marks usually reward
  • Correct relationship lines.
  • Correct use of primary keys and foreign keys.
  • Completed entities with relevant fields.
  • Clear link to the scenario.
Common mistakes
  • Missing PKs.
  • No FK in the joining table.
  • Vague attribute names.
  • Leaving many-to-many relationships unresolved.

Key terms

Entity: thing data is stored about.

Attribute: detail stored about an entity.

Primary key: unique record identifier.

Foreign key: field linking to another table.

Cardinality: how many records relate to each other.

Support section

Class diagrams

Students need to know how to create and read a class diagram, including inheritance pointers and visibility symbols.

How to build a class diagram
  1. Identify classes from the scenario.
  2. Add attributes/properties with data types.
  3. Add methods with brackets and return type if needed.
  4. Add visibility symbols: +, -, #.
  5. Use a hollow arrow for inheritance, pointing to the superclass.
Visibility symbols

+ public = accessible anywhere.

- private = only accessible inside the class.

# protected = accessible inside the class and subclasses.

Inheritance pointer

The arrow points from the subclass to the superclass. For example, Credit inherits from Transaction, so the arrow points to Transaction.

SymbolNameMeaning
+PublicAccessible outside the class
-PrivateOnly accessible inside that class
#ProtectedAccessible inside the class and child/subclass
Transaction
# accountNumber : Integer
# transactionID : Integer
+ getAccountNumber() : Integer
+ getTransactionID() : Integer

△

Inheritance pointer to superclass

Credit
- amount : Real
+ setAmount(amount : Real)
Safe rule: attributes are often private, methods are often public. Use protected only when inheritance makes sense.
Algorithms

Searching & arrays

Linear search

Checks each item in order. Simple and works even if the list is unsorted, but can be slow for large lists.

Binary search

Checks the middle item and halves the search area each time. Faster, but the list must be sorted.

Exam tip: When writing search algorithms, always include a found flag or clear stopping condition, and output a suitable message if no match is found.

Q4 Justification

A CLI or simple kiosk interface is suitable because staff and customers only need to search holidays and enter booking details. Arrays/lists can temporarily store holiday results during a search, while files can store customers, holidays and bookings. Sequential file handling is simple for adding new bookings, although random access could be justified if records are fixed length and the system needs direct access by ID. Validation should include presence checks for names, format checks for email/postcode, range checks for star rating and price, and lookup checks for holiday type. Local variables should be used inside search and booking functions to avoid accidental changes elsewhere. Suitable data types include strings for names and holiday type, integers for IDs and star ratings, reals/currency for prices and Booleans for availability.

Q5 Modes of operation

An online real-time transaction processing system is suitable because bookings must update availability immediately. This helps prevent two customers booking the same holiday. Batch processing is unsuitable for the live booking process because transactions would be queued and processed later, meaning availability may not be up to date. Batch processing could only be useful for non-urgent reports, such as overnight summaries.

Q4 Justification

A CLI is suitable for a prototype because staff can enter client and plumber details using text prompts. Arrays or lists can store plumber records temporarily while searching by speciality, hourly rate or surname. Sequential files are suitable for saving client and plumber records in a small business. Validation should include presence checks for names, lookup checks for speciality, Boolean/type checks for GasSafe and range checks for hourly rate. Local variables should be used inside functions such as addClient() and searchPlumber() to avoid conflicts. Strings should store names and specialities, integers should store IDs, reals should store costs/rates and Booleans should store GasSafe status.

Q5 Backup and recovery

Pete’s Plumbers could use a full backup at the end of each week so that a complete copy of all client, plumber and job records is available. It could use incremental backups daily so only changed files are copied, saving time and storage. Cloud storage would be suitable because the business has limited data and it gives an off-site copy. An external hard drive could be used for a local backup and stored securely away from the main computer. A USB drive could be used for quick transfer, but it is easier to lose and should be encrypted. Recovery should involve restoring the most recent full backup and then applying the later incremental backups.

Q6 Binary search algorithm

declare start is integer
declare endv is integer
declare found is Boolean
declare mid is integer
set start = 0
set endv = 9999
set found = FALSE
input searchValue
repeat
  set mid = (start + endv) DIV 2
  if searchValue = cArray[mid] then
    set found = TRUE
    output "Item found at position", mid
  endif
  if searchValue > cArray[mid] then
    set start = mid + 1
  endif
  if searchValue < cArray[mid] then
    set endv = mid - 1
  endif
until (found = TRUE) OR (endv < start)
if found = FALSE then
  output "Item not found"
endif
